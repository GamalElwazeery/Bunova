# ExecutionKit Antigravity rule

`TODO_FIRST_ENTRY_INVARIANT`: the normal owner entrypoint is the project's canonical `TODO.md` (or configured native authority). If the owner says to open the TODO and execute task-by-task, treat that as sufficient authorization to enter the complete applicable ExecutionKit lifecycle. Internally load root `AGENTS.md` and `execution.config.json`, honor all **eight systems** (Execution, Agent, Content, SEO, Audit, Test, Launch and cross-cutting State), inspect/reconcile live repository truth, refresh native projection when configured, rehydrate State OS, resolve SEO applicability/contract truth when configured, resolve the next canonical lifecycle action, resolve Agent OS context, execute only that action, run task-targeted verification, reconcile canonical TODO/evidence, checkpoint State OS and continue. Do not require the owner to repeat internal bootstrap commands.

Premium Experience is a mandatory cross-cutting product-quality contract for every UI-bearing task; it is **not a ninth OS** and owns no backlog. When work touches Blade/Livewire/Tailwind/Alpine, Flutter/mobile/Dart, Web Components/custom elements, frontend pages/screens, responsive behavior, accessibility, UI, UX, design or components, require Agent OS to resolve the `design-system → component-system → premium-experience` construction chain even when the canonical task omitted a literal `premium` tag. Inspect the project's real design/token authority and component governance before creating UI, extend existing canonical components before creating new ones, use production-shaped data and the required state matrix, and require rendered review across applicable form factors/input modes/accessibility/native behavior. Source existence or a happy-path render is not Premium acceptance; anti-generic review and independent rendered visual acceptance remain evidence gates.

Antigravity `/goal`, when available, is a host persistence mechanism only. It may keep the session alive for multi-hour/multi-day execution, but it is not a scheduler, backlog or completion authority. Continue resolving current canonical truth after each task until closure or a genuine stop condition.

`HOST_CHECKLIST_DERIVED_MIRROR`: when Antigravity exposes a reliable writable Brain/task checklist surface, synchronize it from canonical TODO/lifecycle truth after every canonical task-state mutation and at minimum after each completed task. The Brain/task checklist is derived UI/session state only; it MUST NOT become a second backlog. If that surface is unavailable or not observable, report it as unavailable and do not invent a `brain/task.md` repository path.

`PHASE_BOUNDARY_FULL_CI`: run the applicable smallest targeted verification inside each task lifecycle. Do not dispatch the complete self-hosted CI suite after each ordinary task, commit or push. The portfolio default full-suite run is deliberate/manual at the corrected phase boundary after applicable phase audit/remediation; Launch OS may require another explicit exact-candidate run.

Use the ExecutionKit MCP/skills to inspect canonical lifecycle, State OS and configured SEO OS truth before execution. TODO/native configured task authority owns mutable status. SEO contracts/evidence and State snapshots are derived/control-plane inputs only; findings requiring execution map back to canonical TODO. Work sequentially: one lifecycle action at a time. Do not fork or fan canonical tasks into parallel sessions. Discovery/evidence/runtime/State files under `.executionkit/` are derived artifacts, never a backlog.

For SEO-aware projects:

- prefer the `executionkit_seo_status` MCP tool when available; otherwise run `node .executionkit/runtime/kit/bin/validate-seo.mjs .`;
- treat `NOT_APPLICABLE` as valid only when supported by actual public-surface/product intent;
- route search-facing work through the registered SEO specialists resolved by Agent OS rather than inventing host-only SEO logic;
- never infer indexability from route existence and never claim ranking/indexing/rich-result/traffic outcomes from repository validation;
- before release, rely on the canonical candidate-bound S3 path (`node .executionkit/runtime/kit/bin/release-readiness.mjs .` / `node .executionkit/runtime/kit/bin/validate-seo.mjs . --release`) rather than an ad-hoc Lighthouse result.

When the 3.0 fleet surface is present, Antigravity hook activity may emit a bounded localhost-only presence hint to the shared per-device ExecutionKit Agent. That hint establishes only `HOST_ACTIVE`; it does not prove an agent is executing. Actual `EXECUTION_ACTIVE` state requires runtime/System semantic evidence. Telemetry is best-effort and observational: never block canonical work merely because the local Agent or Elmasna3 server is unavailable, and never put secrets, prompts/transcripts, TODO/source contents or private queues into telemetry.
