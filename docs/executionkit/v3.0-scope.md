# AI ExecutionKit 3.0 — Scope and architecture

**Status:** PUBLISHED 3.0.0 IMPLEMENTATION SCOPE WITH CURRENT 3.x AUTHORITY OVERLAY. The repository distribution is published on `main`; physical-device certification remains direct-evidence dependent. Later 3.x capability additions such as SEO OS extend the authority model without changing the historical fleet-protocol purpose of 3.0.0.

AI ExecutionKit 3.0 turns the existing project-local execution control plane into a fleet-aware, observable, remotely interoperable control plane without weakening project isolation or creating a second backlog/state authority.

3.0 is not "the ExecutionKit Agent release". The local Agent is one runtime component inside a broader major-version contract.

## What does not change

The current 3.x control plane has **eight integrated systems**:

1. Execution OS
2. Agent OS
3. Content OS
4. SEO OS
5. Audit OS
6. Test OS
7. Launch OS
8. State OS

The first seven are capability authorities. SEO OS is conditionally applicable to public organic-search surfaces and may resolve truthfully to `NOT_APPLICABLE`; it is not forced onto API-only, private-panel, desktop-only or native-app-only products. State OS remains the cross-cutting continuity/reconstruction authority and is not capability-leveled.

Fleet monitoring and Elmasna3 integration are **not additional operating systems**. They are observational/control-plane interfaces around the same eight-system model.

`TODO.md`, or an explicitly preserved native canonical task authority with deterministic projection, remains the sole mutable backlog/task-status authority. State OS remains derived/non-authoritative. Elmasna3 remains an external portfolio/control-plane consumer and may not silently become a scheduler or shadow backlog.

## Bootstrap and control-plane independence

ExecutionKit 3.x MUST remain fully capable of planning, selecting, executing, reviewing, testing, auditing, checkpointing and launching canonical project work when no external fleet/control-plane server exists, is configured, is reachable or is healthy.

The external control plane is therefore an optional observability/control integration, never an execution dependency. This is especially important for bootstrapping Elmasna3 itself: Elmasna3 can start as an ordinary ExecutionKit-managed repository, build its own server/client surfaces, then begin observing its own later execution once its compatible ingestion endpoint exists.

Required behavior:

- missing control-plane URL/token is `NOT_CONFIGURED`, not an execution failure;
- unreachable/rejected telemetry is an observability degradation and MUST NOT block canonical local execution;
- local semantic events, State OS and lifecycle authority continue normally while telemetry is offline;
- offline telemetry may spool/replay within bounded policy, but replay MUST NOT mutate canonical task state;
- no project may require Elmasna3 specifically in order to execute ExecutionKit lifecycle actions;
- release/production authorization still comes from the project's normal Launch/operations authority, never from telemetry availability.

Read `docs/architecture/v3-bootstrap-mode.md` for the normative bootstrap-mode contract.

## Major 3.0 capabilities

### 1. ExecutionKit Agent

One lightweight deterministic daemon per developer device, supporting Windows and macOS as required service-install targets. It supervises multiple ExecutionKit worktrees, observes cheap local state, receives host activity hints, transports versioned telemetry, tolerates offline operation and later provides a bounded typed-command bridge.

The Agent is not an LLM and not an Agent OS specialist.

### 2. Fleet/control-plane protocol

A versioned protocol covers at minimum:

- HELLO / capabilities / compatibility;
- presence and heartbeat;
- project/worktree discovery;
- host-active/inactive observation;
- State OS checkpoint observation;
- lightweight Git/worktree observation;
- lifecycle/test/audit/launch/evidence events where produced by existing authorities;
- diagnostics;
- future artifact transport;
- future decisions/approvals;
- future typed commands and results.

Protocol events are observations with provenance and idempotency. They never mutate canonical task state by themselves.

### 3. Active-project awareness

ExecutionKit 3.0 must distinguish:

- Agent online;
- worktree known;
- host recently active;
- runtime/lifecycle action proven active;
- State checkpoint fresh/stale;
- unknown/stale evidence.

For Antigravity, the ExecutionKit host hook emits a localhost-only best-effort activity pulse for one unambiguous ExecutionKit workspace. A pulse proves recent host activity for that workspace, not task completion, context percentage, model thinking, or authorization.

Same repository on Windows and macOS remains two distinct worktrees/machines. They must never be merged into one invented active state.

### 4. State OS telemetry integration

State OS remains the continuity authority. 3.0 adds a sanitized observation projection for external control planes and the Agent transports it.

High-frequency telemetry must not trigger full State fingerprint generation. Semantic State checkpoints remain event-driven/milestone-driven. The Agent watches State checkpoint metadata and reads the small latest snapshot only when changed.

### 5. Lifecycle/system event integration

Execution OS, Agent OS, SEO OS when applicable, Audit OS, Test OS and Launch OS use the common local event/evidence boundaries for meaningful transitions without transcript scraping. Content OS remains the content authority feeding applicable search/content contracts; State OS records bounded continuity facts around those transitions.

Examples:

- lifecycle action selected/resumed/completed;
- canonical blocker encountered;
- reviewer route selected;
- SEO applicability/gate state where emitted by the owning SEO validator;
- audit boundary started/completed;
- tests selected/started/completed;
- candidate/evidence/release gate transitions;
- State checkpoint/rehydration transitions.

Events must carry evidence/provenance and cannot create a separate mutable task list.

### 6. MCP expansion

The project-local MCP server gains read-only 3.0 surfaces for:

- local Agent status;
- registered worktrees/device identity where appropriate;
- fleet compatibility/telemetry configuration status;
- sanitized control-plane observation status;
- explicit local telemetry flush/diagnostics where safe.

Current 3.x MCP also exposes the applicable SEO status/validation surfaces through the SEO authority. Later command surfaces remain typed and policy-gated. MCP never becomes task authority.

### 7. Host adapter contract

Host integrations become explicit adapters with capability truth. Initial required host is Antigravity on Windows/macOS.

An adapter may claim only capabilities it can prove. Host adapters must not use brittle UI automation as a foundational contract and must not claim access to private model context/thinking when the host does not expose it.

OpenCode and other hosts are added only through verified supported integration mechanisms.

### 8. Project bootstrap/adoption/migration

New and migrated projects receive compatible 3.0 host/telemetry surfaces without forcing per-project daemons. Current 3.x bootstrap/adoption also reconciles SEO OS as a first-class capability authority, with applicability evaluated from real public-search surfaces and a canonical `EK00-005S` deep-integration decision before Audit/Test/Launch closure.

The device Agent remains user-local. Projects contain only safe integration metadata/hooks/config references required for discovery and telemetry. Secrets/tokens remain outside the repository.

Migration must preserve:

- canonical TODO bytes/status during mechanical tooling migration;
- stronger native project agents/resources;
- existing State OS history semantics;
- existing project-specific SEO decisions/contracts unless explicitly replaced;
- manual self-hosted CI policy;
- project-specific host/editor behavior.

### 9. Fleet integration and registration

3.0 adds fleet-aware CLI/doctor behavior for discovering which registered worktrees on the current machine are compatible/current/stale without crossing project authority boundaries.

Registration links local worktrees to the external control plane using stable device/worktree/repository identities. Remote control remains disabled until explicitly authorized.

### 10. Resource/network efficiency

3.0 treats efficiency as a release requirement, not an optimization after launch.

Default principles:

- one daemon per device, never one per repo;
- no busy-loop scanning;
- active/inactive adaptive intervals;
- cheap file metadata sentinels before content reads;
- never parse/upload huge TODO on every heartbeat;
- delta-only semantic events;
- bounded heartbeat cadence;
- gzip batched HTTPS transport;
- at most one default in-flight upload;
- bounded offline spool with coalescing;
- optional machine CPU/memory telemetry disabled by default;
- no source-code/transcript upload in routine telemetry.

### 11. Security and privacy

3.0 requires:

- outbound-only control-plane connectivity from developer devices;
- localhost-only host pulse listener;
- TLS for remote telemetry by default;
- per-device identity and revocation-ready enrollment;
- secrets outside project Git;
- bounded/sanitized payloads;
- local paths hidden by default;
- no generic remote shell contract;
- typed future commands with exact target, TTL, idempotency, expected-state guard and local policy revalidation;
- immutable result/audit evidence on the control-plane side.

### 12. Elmasna3 compatibility contract

Elmasna3 is the initial 3.0 external control plane and reference implementation, but the protocol must remain ExecutionKit-owned/versioned rather than hardcoding business logic into the local daemon.

The compatibility handshake distinguishes:

- ExecutionKit distribution version;
- Agent version;
- telemetry protocol version;
- supported capabilities;
- project State/config schema compatibility;
- control-plane supported protocol range.

Version mismatch produces an explicit upgrade/unsupported state, never silent partial truth.

Elmasna3 availability itself is not required for ExecutionKit execution. A compatible third-party control plane, a temporarily offline Elmasna3 server or no configured control plane at all must leave local lifecycle execution valid.

### 13. Validation and distribution

Current 3.x certification cannot be declared from documentation presence. Distribution validation must mechanically cover:

- required Agent runtime/CLI/schema/docs files;
- current seven-capability + State #8 authority semantics;
- SEO contract/schema/model/validator/Agent routing and bootstrap/migration coherence;
- SEO applicability truth and release fail-closed behavior for enabled public-search surfaces;
- host pulse integration;
- Agent protocol/schema conformance;
- no TODO authority duplication;
- local-path privacy defaults;
- HTTPS default policy;
- bounded spool/batch settings;
- Windows/macOS service-install generation/behavior where testable;
- giant-TODO no-repeat-parse regression;
- duplicate/out-of-order/offline replay behavior;
- State OS observation compatibility;
- MCP/doctor/bootstrap/migration coherence;
- Antigravity hook remains non-blocking when Agent is absent;
- local execution remains valid when the external control plane is missing, unconfigured or unreachable;
- preserved historical 2.2.4 regression semantics remain green when executable certification evidence is produced.

Repository publication must preserve any missing executable/physical evidence as `NOT_RUN`/`UNVERIFIED`; it must never translate static presence into PASS.

## Implementation waves

These are architecture waves, not a second mutable backlog.

### Wave A — Contracts and read-only local Agent

Protocol/schema, one-daemon architecture, machine/worktree identity, registry, active Antigravity workspace pulse, State checkpoint observation, lightweight Git/TODO sentinels, batching/backoff/offline spool, Windows/macOS service lifecycle.

### Wave B — ExecutionKit system event bus

Introduce one internal semantic event API and wire meaningful Execution/State/Agent/SEO/Audit/Test/Launch transitions into it without transcript scraping or task duplication.

### Wave C — MCP/doctor/bootstrap/migration/distribution

Expose status/diagnostics, install/update project hooks, validators and documentation, and prove old integrations still migrate safely. Current distribution coherence includes the SEO OS overlay and its conditional applicability semantics.

### Wave D — Elmasna3 server integration contract and executable conformance

Freeze compatibility/enrollment/telemetry ingestion/projection semantics against an executable reference control-plane conformance suite. Elmasna3 product implementation then consumes that frozen protocol at its canonical product frontier rather than forcing ExecutionKit publication to depend on an unfinished product repository.

### Wave E — Decisions/artifacts/typed commands

Only after read-only telemetry is stable and independently audited: artifact transport, owner decision/approval bridge, then bounded typed commands. Arbitrary shell remains out of scope by default.

## Publication and certification rule

The published repository version remains `3.0.0` until an explicitly approved version-promotion task changes it. Publication requires coherent version/config/manifest/documentation surfaces and must preserve evidence boundaries honestly.

Publication alone MUST NOT be described as an executable `npm run check` PASS, a macOS/Windows certification, an installed Agent-service proof, IDE activation proof, independent command-level final audit, SEO indexing/ranking proof, or fleet-connectivity proof unless the corresponding direct evidence actually exists.

Physical-device certification is performed at the real device/adoption boundary according to `docs/operations/v3-release-validation.md`; the current publication/certification status is defined in `docs/operations/v3-publication-status.md`.

Projects may adopt the published 3.x distribution immediately, including Elmasna3 in Bootstrap Mode, but each project must still complete its own applicable deep-integration and SEO/Audit/Test/Launch acceptance gates before claiming project-specific conformance or release readiness.

Future versions may make exact-SHA physical certification a blocking publication dependency through their canonical TODO. If so, that dependency must be honored or explicitly cancelled/superseded with rationale; it may never be silently skipped or called PASS.
